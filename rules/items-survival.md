## アイテムとサバイバル

- **アイテム ID の 1..63 はブロック ID と同じ番号**（置けるアイテム）。64..94 が棒・鉱物・道具。
  ここまでは**凍結**です（`localStorage` に番号がそのまま入っているので振り直せません）。
  **新しいアイテムは 111 から**（`SHARED_ID_START`）。**95..110 は空けたままにすること** ——
  ブロック側の向き違いが使っている番号で、111 以降は**ブロックとアイテムで 1 本の番号列**です
  （`CLAUDE.md` の「ブロック ID の枠」）。番号は `ROADMAP.md` の予約表から取ります。
- **111 以降にブロックを足したら、`items.ts` の `MAX_ITEM_ID` も伸ばすこと。**
  ブロックのアイテムは `items.ts` の `for (const block of BLOCKS)` が
  **`variantOf === AIR` のブロック全部に自動で作ります**（だから `item({...})` を
  手で足すと**同じ番号が二重に登録されます**）。ところが一覧を作る `allItemIds()` は
  **`1..MAX_ITEM_ID` を数え上げるだけ**なので、伸ばし忘れると
  **`ITEMS` には入っているのにクリエイティブの一覧（`craftscreen.ts` の
  `CREATIVE_ITEMS`）にだけ出てこないブロック**ができます。置けるし掘れるし
  レシピも通るので、**型でも `npm run typecheck` でも止まりません**
  （2026-09-04・鉄／金／ダイヤのブロックの周。`test/blocks.test.ts` の
  「共有帯のアイテムは…25 個」と `MAX_ITEM_ID` の突き合わせが唯一の足場です）。
- **「`items.ts` は 0 行」と書いてある仕様書でも、`MAX_ITEM_ID` の 1 行だけは別です。**
  2026-09-05 のキノコ（139 / 140）の仕様書が「`src/items.ts` は**1 行も要りません**」と
  書いていましたが、**伸ばさないと `allItemIds()` が 1..138 しか数えず、
  クリエイティブの一覧に出てこないブロックが 2 つできます。** 仕様書の「触らない
  ファイル」より**この決まりごとが勝ちます**（`AUTODEV.md` の B は仕様を 1 枚に
  収めるためのもので、`rules/` を上書きする権限はありません）。
  **気付ける足場は「共有帯のアイテムが何個か」を数で見張っている件だけ**です ——
  一覧の名前だけを見ていると、**名前が増えていないことに誰も気付きません。**
- **`MAX_ITEM_ID` を新しいアイテムへ移すと、それまで指していたブロックの import が
  余ります。** `MAX_ITEM_ID = DIAMOND_BLOCK` を `= MILK_BUCKET` に直した瞬間、
  **`items.ts` の `DIAMOND_BLOCK` が「使われていない」で `npm run typecheck` が落ちました**
  （2026-09-05・ミルクバケツの周）。ブロック側のアイテムは
  `for (const block of BLOCKS)` が作るので、**あの import は `MAX_ITEM_ID` の 1 か所
  でしか使われていません** —— 移したら import も一緒に消すこと（型で止まるので安全な罠です）。
- **何が落ちるかを決めるのは `items.ts`。** 山を全部（0〜2 山）返すのが
  **`rollDrops(blockId, roll): readonly DropStack[]`** で、**呼ぶのは `breaking.ts` の
  1 か所**（掘って壊す `tryBreak()` と、支えを失って壊れる `autoBreak()` が同じ
  `harvest()` を通ります）。**2 つの経路を別々に書かないこと** —— 片方だけ直すと、
  掘ったときと床を抜かれたときで落ちるものが食い違います。
  **`rollDrop()`（1 山目だけを返す旧来の関数）は残してあります。** 既存の約 25 か所の
  テストの根拠なので、名前も引数も戻り値も変えないこと。`rollDrops()` の 1 山目も
  **`rollDrop()` を呼んで**作ります（`chance` / `otherwise` の判断を 2 か所に写さないため）。
- **2 山目は `Drop.extra?: DropStack`**（`item` と `count` だけ）。**1 山目の当たり外れに
  関係なく必ず落ちます** —— 別の山だからです。いま持っているのは**実った小麦の 1 行だけ**
  （小麦 1 + 種 1）で、`test/blocks.test.ts` が「`extra` は 1 山目と別のアイテム」と
  「どのブロックでも山は 2 つまで」を全ブロックで見張っています。
- **`extra` に `chance` や個数の範囲（min / max）を持たせないこと。** 流れてくる乱数は
  `BreakOrder.roll` の 1 本だけなので、付けると**1 山目の当たり外れと必ず相関します**
  （砂利の火打石と種の個数が連動する形）。本家の「小麦 1 + 種 0〜3」に寄せたいなら、
  **乱数をもう 1 本流す話が先**です（`BreakOrder` と `autoBreak()` の引数と `main.ts` に及びます）。
- **山が 2 つでも、`harvest()` は同じ座標に貼るだけ**でよい。地面での散らばりは
  `drops.ts` の `burst()` が乱数で付けるので、**`breaking.ts` や `drops.ts` に
  「2 山を並べて置く」を書かないこと。**
- **`main.ts` に確率の比較を書かないこと** —— `test/ui.test.ts` が `main.ts` に
  `.chance` が、`test/breaking.test.ts` が `rollDrop(` / `rollDrops(` / `canHarvest(` が
  出てこないことを見張っています。`Drop.chance` を外したときに何が落ちるかは
  **`Drop.otherwise`**（省略すると何も落ちない）。**砂利がこれのためにあります** ——
  10% で火打石、外したら砂利そのもの。`otherwise` を落とすと、**掘ると 90% で消えるブロック**
  になります（葉は逆に、外したら何も出ないのが正しい）。
- **落とし物を「自分以外のもの」に差し替えたら、戻す道を同じ周で用意すること。**
  **雪（`SNOW`）は掘ると雪玉 4 個**になるので、`crafting.ts` の「雪玉 4 個 → 雪ブロック 1 個」
  が無いと**雪が二度と置けなくなります**（砂利・草むらの `otherwise` は「自分が戻る」ので
  この問題が起きません。**別のものに差し替えたときだけ**の罠です）。
  **戻すレシピの側で個数を変えないこと** —— 落ちる 4 個と戻す 4 個が食い違うと、
  掘って戻すだけで雪が増えるか目減りします。
- 確率つきドロップのテストは**種を固定した乱数 1 本を回し続けること**
  （`seeded()` を 1 件ずつ作ると、線形合同法の 1 個目が種に引きずられて偏ります）。
  境目は乱数ではなく **`rollDrop(id, 0.05)` のように値を直に渡して**確かめられます。
- 採掘時間は Minecraft と同じ式（`mining.ts`）: `硬さ × (適正なら 1.5 : 5) / 道具の速さ`。
  「適正」= 道具の種類が合っていて階層が `minTier` 以上。**種類だけ合っていて階層が足りない道具は、
  速くはなるが何も落とさない**（石のツルハシでダイヤ鉱石を掘っても消えるだけ）。
- 形ありレシピは**盤面もレシピも空の行・列を落としてから**比べます（`crafting.ts` の `trim`）。
  レシピ側のトリムを忘れると、斧のように右端が空いた形が永久に一致しません。左右反転も受け付けます。
- インベントリ・クラフト・採掘の計算は DOM に触らないので、全部ヘッドレスでテストできます。
  **判定を `inventoryui.ts` 側に書かないこと**（`rules/inventory-screen.md`）。
- クリエイティブへ切り替えるときは**空いているホットバーだけ**を埋めます（上書きすると集めたものが消えます）。
  `PALETTE` はホットバーの 9 枠に合わせて **9 個まで**。溢れた分は黙って消えます。
- 松明は床にも壁にも置けます。向きは**別のブロック ID**（`WALL_TORCH_*`）で表していて、
  ボクセルにメタデータは持たせていません。名前・アイテム・ドロップは `variantOf` で
  大元の `TORCH` に寄せてあるので、**置き方を増やしてもアイテム欄は増えません。**
  置き方を足すときも同じ形にしてください（`torchVariant()` と `TORCH_BY_SUPPORT` の表）。
- **バケツは空・水・溶岩の 3 つで 1 組**（中身をアイテム ID で表すのは Minecraft と同じ）。
  **積めるのは 1 個まで** —— 16 個の水を 1 枠に持てると水路作りが別のゲームになります。
  - 対応の表は `items.ts` の **`FILLED_BUCKETS` 1 か所**。液体を足すときはここに 1 行で、
    **`item === WATER_BUCKET ? ...` のような分岐を書かないこと**（汲む側と流す側の
    2 か所を直すことになり、必ず片方を忘れます）。液体全部にバケツがあることをテストが見ています
  - 汲む／流すの判断は **`bucketUse()`（純粋。座標を知りません）**。
    **どのマスに効くかは `placing.ts` の `tryBucket()`**（汲むなら狙ったマス、流すなら置くマス）で、
    `main.ts` は光線を引き直して結果を貼るだけです（`tryPlace()` / `tryIgnite()` と同じ形）
  - **バケツを持っているときだけ、狙う光線が液体に当たります**（`raycastVoxels` の
    `hitLiquid`）。既定は素通りのままにすること —— 変えると溶岩湖の向こうを狙ったときに
    手前の溶岩が置き場になる、あの壊れ方が戻ります
  - **クリエイティブでも中身は入れ替えます。** バケツは「減る道具」ではなく
    中身そのものがアイテムなので、入れ替えないと永久に空のままで何も流せません
- **エンダーアイでクリア導線の 2 本が合流します**（ネザー要塞のブレイズロッド →
  ブレイズパウダー、と、夜のエンダーマンのエンダーパール）。**どちらの材料も
  モブの落とし物しか出どころがありません** —— 生成や別のレシピで手に入る道を足すと、
  要塞にも夜にも行かずにエンドへ行けるようになります（進行テストがここを見張っています）。
  - **ロッドから直接アイを作る形を足さないこと。** パウダーの 1 → 2 が飛ばされて、
    枠 12 個ぶんに要るロッドが 6 本から 12 本に増えます（＝要塞に通う回数が倍）。
  - **エンダーアイのスタック上限は 64、エンダーパールは 16** と食い違わせてあります。
    枠 12 個ぶんがどちらも 1 枠に収まる、という一点だけが理由です
    （`test/crafting.test.ts` が 12 個を数えて見張っています）。

**かまどが入ったので、精錬の代用 2 つは戻してあります**（鉄と金の鉱石は鉱石のまま落ち、
砂 4 個 → ガラスのクラフトは消しました）。`rules/stateful-blocks.md` の「かまどと精錬」を見てください。
**道具の耐久値は `durability.ts`** です。**傷はインベントリ・クラフト画面・地面の落とし物・
チェスト・かまどまで付いて回ります**（セーブは `wear` / `craftWear` / `dropWear` /
`chestWear` / `furnaceWear` の 5 つの省略可キー）。**読んだ値をどこまで信じるかは
`wornValue()` 1 本**で、最大以上は `最大 - 1` に丸めます（そのまま入れると
「壊れているのに手に残っている道具」になります）。**傷が消える経路はもう 1 つも残っていません。**

**傷が付く物は 4 種類あって、減り方が違います**（判断は全部 `durability.ts`）。

| 減り方 | 何が | 何回 | どこで減るか |
| --- | --- | --- | --- |
| **掘って減る** | ツルハシ・斧・シャベル 12 本 | 木 59 / 石 131 / 鉄 250 / ダイヤ 1561 | `wearForBreaking()`（`breaking.ts` の `tryBreak()` が返す `wear`） |
| **使って減る** | 火打石と打ち金・弓・**シアーズ** | **64 / 384 / 238**（本家のまま） | `wearForUse()`（`main.ts` の `igniteAt()` と `loose()` と `shearMob()`） |
| **殴って減る** | 剣 4 本 | 掘る道具と**同じ階層の表**（59 / 131 / 250 / 1561） | `wearForAttack()`（`main.ts` の `mousedown` の `attack`） |
| **耕して減る** | クワ 4 本 | **59 / 131 / 250 / 1561**（掘る道具と同じ `TOOL_USES`） | `wearForTill()`（`main.ts` の `tillAt()`） |

- **この 4 つを混ぜないこと。** 火種と弓に `tool:` を付けると `ToolDef` は
  「掘る速さ」の表なので**弓で石が速く掘れます**し、`wearForBreaking()` から
  「掘る道具でなければ 0」を外すと**弓で石を掘って弓が減ります。**
  逆に `wearForUse()` が掘る道具に 1 を返すと、**ツルハシを右クリックしただけで減ります。**
  **`wearForAttack()` を `wearForUse()` に混ぜるのも同じ罠で、剣を右クリックしただけで減ります。**
- **剣は掘っても減ります**（`wearForBreaking()` が 1 を返す。本家と同じ）。
  `toolOf()` が非 null なので**1 行も足さずに付いてきます** —— 外さないこと。
- **ツルハシ・斧・シャベルは殴っても減りません。** 本家は減りますが、
  ここでそう変えると**既存 12 本の寿命が黙って縮みます**（掘るための回数のまま戦闘ぶんが乗る）。
  変えるならユーザーと決めてください。
- **剣 4 本（木 111 / 石 112 / 鉄 113 / ダイヤ 114）は「殴るための道具」です。**
  `ToolKind` に `"sword"` を足しただけで、**耐久値もセーブの 5 キーも 1 行も書かずに
  付いてきます**（`maxUses()` が `toolOf()` に聞くだけなので）。
  **`TOOL_USES` に剣用の 5 つ目の表を作らないこと。**
- **どのブロックにも `tool: "sword"` を付けないこと**（`test/blocks.test.ts` が見張っています）。
  付けた瞬間、剣がそのブロックの採掘道具になって速く掘れます。**掘る速さは
  `speed: 1`**（素手と同じ）で、`TIER_SPEEDS` を渡さないこと。
- **どれが剣かは `items.ts` の `isSword()`**（`toolOf(id)?.kind === "sword"`）。
  火種・弓と違って表を持たないのは、剣が 4 本とも `ToolDef` を持っているからです。
  **`durability.ts` に `item === WOOD_SWORD` と書かないこと**（`test/durability.test.ts` が見張り）。
- **攻撃力は `mobs.ts` の `TOOL_ATTACK` に 1 行**（`sword: 4`）。剣 4.5 / 5 / 5.5 / 6 で、
  **ダイヤの剣（6）がダイヤの斧（5）より強い**。本家は 4/5/6/7（階層ごとに +1）ですが、
  ここは `TIER_ATTACK` が 0.5 なので伸びが半分です（`TUNING.md`）。
- **減らすのは「殴れたとき」だけ。** `mobs.attack()` は**クールダウン中なら false** を返すので、
  `main.ts` はその戻り値の中でだけ `wearHeld(wearForAttack(...))` を呼びます
  （**戻り値を捨てて呼ぶと、連打しただけで剣が減ります**）。
  `test/durability.test.ts` が `main.ts` の `wearForAttack(` を**1 回**と数えています。
- **どれが火種・弓・シアーズかは `items.ts` の `isFireStarter()` / `isBow()` / `isShears()` の表 1 本**です。
  `durability.ts` に `item === BOW` と書き始めると、種類が増えたときに
  「持てる側」と「減る側」の 2 か所を直すことになり、必ず片方を忘れます
  （`test/durability.test.ts` が `durability.ts` にアイテムの名前が出てこないことを見張っています）。
- **減らすのは「効いたとき」だけ。** 矢が無い・引きが足りない・火が点かなかった
  （`blocked` / `none`）ときは 1 も減りません —— **`main.ts` は早期 return より後ろで
  `wearHeld(wearForUse(...))` を呼びます。** 前へ動かすと空撃ちで弓が減ります。
- **`main.ts` に回数（64 / 384 / 238）と「弓かどうか」を書かないこと。**
  `test/durability.test.ts` が `main.ts` に `384` が無いことと、`wearForUse(` が
  **点火・発射・刈るの 3 か所から**呼ばれていることの両方を見ています（減っていたら配線が落ちています）。
- **どれがクワかは `items.ts` の `isHoe()` の表 1 本**です（`isSword()` と同じ形）。
- **`wearForUse()` にクワを混ぜないこと。** あちらは「掘る道具でないもの」の表で、
  クワは `toolOf()` を持つので 0 が返ります。**右クリックしても減らないのが正しい** ——
  減るのは**耕せたときだけ**（`placing.ts` の `tryTill()` が `placed` を返したときだけ
  `main.ts` が呼びます）。**逆に `wearForBreaking()` からは外さないこと** ——
  **クワで掘れば減るのは剣と同じ**で、1 行も足さずに付いてきます。
- **`main.ts` の `wearForTill(` は 1 か所だけ**（`test/durability.test.ts` が見張っています）。

**シアーズに `tool:` を持たせないこと。** 剣は `ToolKind` に 1 語足すのがいちばん安かった
（耐久値もセーブの 5 キーも 1 行も書かずに付いてくる）のですが、**シアーズで同じことを
すると壊れます**: `mobs.ts` の `TOOL_ATTACK` に無い種類が入ると `attackDamage()` が
`undefined + 0.5 * tier` = **NaN** を返し、`wearForBreaking()` は「掘る道具」として 1 を
返すので**石を掘るたびに減ります。** **新しい道具を足すときは、`ToolKind` に足すかどうかより
先に「減り方の 4 種類のどれか」を決めること。**

**`ToolKind` に 1 語足すときは、その逆側にも注意が要ります。** 剣と同じくクワは
`ToolKind` に足して正解でしたが、**`mobs.ts` の `TOOL_ATTACK` に `hoe: 1` を足すのを
忘れると `attackDamage()` が `undefined + 0.5 * tier` = NaN を返し、クワで殴ったモブの体力が
NaN になって二度と死にません。** `TOOL_ATTACK` は `Record<string, number>` なので
**typecheck は通ります**（`TOOL_NAMES` は `Record<ToolKind, …>` なので教えてくれる、という
非対称がここにあります）。**`test/mobs.test.ts` に「クワで殴っても NaN にならない」があります。
次に `ToolKind` を増やす人も同じ 1 行を足してください。**
- **セーブは 1 バイトも増えていません。** `serializeWear()` も `wornValue()` も
  `maxUses()` に聞くだけなので、**`maxUses()` が 0 でなくなった瞬間に
  `wear` / `craftWear` / `dropWear` / `chestWear` / `furnaceWear` の 5 つ全部に自動で載ります**
  （`SaveData.version` は 1 のまま）。

### 食べ切ると器が戻るもの（`EMPTIES`）

**何が戻るかは `items.ts` の `EMPTIES` の表 1 本**（`emptyAfterEating()`）。いま入って
いるのは**キノコシチュー（142）→ ボウル（141）の 1 行**だけです。

- **`main.ts` に `held === MUSHROOM_STEW` と書かないこと。** 配線が持ってよいのは
  「引いて、`NO_ITEM` でなければ手に貼る」の 3 行だけで、`test/ui.test.ts` が
  **`main.ts` に `BOWL` も `MUSHROOM_STEW` も出てこない**ことと、
  **`emptyAfterEating(` を呼び直している**ことの両方を見張っています。
- **`vitals.ts` に置かないこと** —— あちらは持ち物の表を import しません
  （`FoodValue` と `FoodDef` を構造で合わせてあるのと同じ線）。
- **器が戻る食べ物は `stack: 1` にすること。これは手触りではなく不変条件です。**
  戻すのは `inventory.setSelected(器, 1)` なので、**2 個以上積めると 1 個食べただけで
  残りの山ごと器 1 個に潰れます**（食べたのは 1 個なのに山が消える）。
  `test/blocks.test.ts` の「シチューは 1 枠 1 個」が唯一の足場です。

### 道具の耐久値（`durability.ts`）

**判断は全部 `durability.ts`** にあります（`vitals.ts` と `ui.ts` の関係と同じ形）。

| ファイル | 中身 | 確かめ方 |
| --- | --- | --- |
| `durability.ts` | **判断は全部ここ。** 回数の表・減るか・壊れたか・帯の割合・1 行・セーブの形 | `npm test` |
| `inventory.ts` | `Slot.damage` を持つだけ（書き出し・読み戻しは委譲） | `npm test` |
| `ui.ts` | `wearBar()` の割合を `style.width` に貼るだけ。**数値を書かない** | ブラウザ |

- **回数の表（`TOOL_USES`）を `items.ts` の `ToolDef` に持たせないこと。** あちらは
  「掘る速さ」の表で、混ぜると耐久値を触るたびにアイテムの表ごと動かすことになります。
  **速さと回数は別の表**です（片方だけ触ると「速いのにすぐ壊れる」が作れます）。
- **`durability.ts` が `inventory.ts` から取ってよいのは `import type { Slot }` だけ。**
  逆向き（`inventory.ts` → `durability.ts`）は普通の import なので、値を取ると輪ができます。
  だから `wearSlot()` は `clearSlot()` を呼ばず、自分で 3 つの値を戻します。
- **傷を捨てる／持っていく場所は 5 つで、全部 `inventory.ts` にあります**:
  `empty()` / `clearSlot()` / `addToSlots()` の空き枠 / `setSelected()` は 0 にし、
  **`swap()` だけが持っていきます。** 1 つでも忘れると、収納へ移した道具が新品に戻ります。
- **セーブは `SaveData.wear`（36 要素・省略可）。** `inventory` の `[item, count]` を
  3 要素にしないこと —— 既存のセーブが丸ごとずれます。**全部新品なら書き出さない**ので、
  道具を傷めていない人のセーブは耐久値が入る前と 1 バイトも変わりません。
  読み戻しは **`deserialize()` のあと**（何回使える道具かは中身で決まります）。
  **最大以上の値は `最大 - 1` に丸めること** —— そのまま入れると「壊れているのに
  手に残っている道具」になります。
- **傷はインベントリの 36 枠だけでなく、クラフト画面・地面の落とし物・器の中身にも乗ります**
  （3b / 3c-1 / 3c-2・2026-09-01）。**どれも中身の配列を増やさず、別の省略可キーで持ちます**
  （`rules/inventory-screen.md` / `rules/drops.md` / `rules/stateful-blocks.md`）。
  運ぶ側が使ってよいのは `damageOf()` / `carryWear()` / `wornValue()` までで、
  **`?? 0` をその場ごとに書かないこと。**
- **耐久値は速さにも収穫にも効きません**（`mining.ts` の `breakTime()` / `canHarvest()` は
  傷を見ません）。減っても最後の 1 回まで同じ速さで掘れます（本家と同じ）。
- **減らないものを増やすときは `wearForBreaking()` の 4 つを見ること**:
  クリエイティブ / 道具でない物（素手を含む）/ 壊せないブロック / **硬さ 0**（松明・草）。
  **支えを失って壊れたぶん（`autoBreak()`）も減りません**（道具を見ない経路なので）。
